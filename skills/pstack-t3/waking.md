# Waking and scheduling in T3 Code

Read this before a step waits on an event, loops, schedules a run, builds an automation, pauses a program, or picks one up. The names map as in [the T3 Code adapter](SKILL.md).

| Cursor | T3 Code |
| --- | --- |
| `/loop` (Cursor's built-in wake mechanism) | Pick the T3 wake for what you wait on. A child's completion wakes you with no call, so end the turn. A PR event (checks finish or fail, a new comment or review, a conflict) is `watch_pull_request`, as the adapter's Pull requests rows say. On Claude and OpenCode, a command you started, such as a test run or a build, runs as the session's background command. Its exit wakes you, and `t3_background_wait` with its task id keeps the thread shown as working until then. On another provider, run it in the foreground. Any other event is an async `delegate_task` watcher, a small script that blocks until the event, whose completion wakes you. A heartbeat is `schedule_task` with the tick text in `prompt` and `schedule` set to `{"type":"interval","everyMs":<ms>}`, bound to this thread. `everyMs` is at least 60000. One wake at a set time is `{"type":"once","runAt":"<time>"}`. `/loop until X` puts the predicate in the tick prompt, and the tick that sees it met calls `delete_scheduled_task`. |
| `/loop 1h` | `schedule_task` with `schedule` set to `{"type":"interval","everyMs":3600000}`. Keep the literal text `/loop 1h` where a plan or status message names it, because `poteto-mode/scripts/check-plan.mjs` checks for it, and record the scheduled task's id beside it. |
| Cursor Automations: routines, `update_state` routine calls, `api2.cursor.sh/automations` webhooks, routine wakes | `schedule_task`, with the trigger in `schedule` and the text in `prompt`. A timed routine is `{"type":"interval",...}` or `{"type":"fixed_time","timeOfDay":"09:00","weekdays":[1,2,3,4,5]}`. A webhook routine is `{"type":"webhook"}`. Only the call that creates it returns its `webhookUrl`, and only with T3 Connect and run permission. If it is absent then, tell the user to enable T3 Connect remote access. The run sees the request only through `{{body.<field>}}`, `{{headers.<name>}}`, `{{body}}`, or `{{request}}` placeholders in the prompt, so put them there. Set `bindToCurrentThread: false` only when the user wants a fresh thread per run. |
| `SendToUser` secret requests, sender keys | `request_secret`. With its default delivery you never see the value, and its `secretRef` works once, as a webhook `signature.secretRef` for a sender that signs with HMAC-SHA256, such as GitHub. With `delivery: "file"` it gives a file that one command reads, which is how a server you build gets a secret. |

On Claude, `Monitor` can watch a log or a file for an event that is neither a PR event nor a child's completion. Pass `t3_background_wait` only a task id that an earlier call returned, never one you guess in the same message as the command. Never wait with a foreground `sleep`, which Claude Code blocks.

Every schedule you create is program state. Record its id in the decision trail or status file. On a hold, a stand-down, or Pause safely, pause it before you send any stop order, and say so. To pause one, call `schedule_task` with its `scheduledTaskId` and `enabled: false`. A tick prompt that can dispatch work starts by reading the hold state and does nothing while it is held. Delete the schedule when the program ends.

## Pause safely and Session pickup

At a pause, pause every schedule the program created, then stop running children with `task_cancel`. Messages sent while a thread is busy wait in its queue. On resume or pickup, read the thread with `t3_thread_read`, then list its queued messages with `t3_queue`, `action: "list"`, and that thread's `threadId`. A queued message can change the plan, so handle it before the resume note's first action.
